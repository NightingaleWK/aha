# 本机成品交付与临时文件清理

## 1. 范围与触发条件

aha 是用户双击使用的 Windows 本机工具。用户要求实施可见功能或修复后，默认交付与最终源码一致的桌面单文件 EXE，并主动完成临时文件清理；在提交、归档或结束会话前检查本规范。用户明确仅要设计、评审或源码时遵守其范围，纯文档修改无需重新打包。

本机交付不包含远端推送、对外发布、安装服务或修改真实业务资料。既有授权跨回合复用；任务已归档也不能成为停止已授权交付或清理的理由。

## 2. 操作入口

使用既有 [构建脚本](../../../scripts/build_windows.py)，不另造发布链：

```text
python scripts/build_windows.py --build-root <任务自有Windows目录> --stage Directory
python scripts/build_windows.py --build-root <同一目录> --stage OneFile --directory-verified
aha.exe --data-dir <独立合成资料目录> --no-browser
```

解释器必须为原生 Windows x64 隔离环境，通过既有 SQLite 门禁。先实际验收 Directory，再使用 `--directory-verified`；参数本身不构成验收。默认保留托盘，只有无桌面检查才显式使用 `--no-tray`。

通过 Windows KnownFolder/系统桌面接口确认实际桌面，不能固定用户路径或假定桌面不在 OneDrive。默认成品名为 `aha.exe`；同名文件先核实归属、版本与占用，保留必要的可恢复旧版，不覆盖未识别文件或强杀不明进程。

## 3. 交付、预览与清理合同

### 成品与证据

- 实施计划包含成品类型、实际交付位置和运行方式；默认桌面交付纳入同一任务验收，不留到用户再次提醒。
- 记录构建的源码依据（提交或工作树指纹）、产物 SHA256、运行时和实际执行的检查。最后一次产品源码修改后必须重新构建对应成品。
- Directory 与 OneFile 分别验证原生程序、实际 HTTP/页面、资源、相关业务及退出；有材料变化时核对 Excel/打印，区分独立验收与已核实的输出一致性。要求见 [质量规范](quality-guidelines.md)。
- 交付副本与验收产物 SHA256 一致；从实际桌面文件再次启动，使用隔离合成资料检查主要功能、重开/原包、退出及运行描述符清理。OneFile 的 bootloader 父子进程不能误判为两个服务。
- 最终说明包含用户可找到的文件路径、启动方式和已验证结果。不能只提供 Git 提交号、源码目录、测试预览或依赖整套目录的 EXE。

### WSL 预览

- 交互 HTML 通过本机 HTTP 服务展示，在应用内浏览器打开并给出当次有效链接；不要反复尝试已失败的内联路径。浏览器打开结果为 queued 时不能声称已经打开。
- 临时地址、端口和认证随实例变化。需要启动凭证时通过打开工具传入私有地址，公开说明只提供适合展示的链接，不抄入 token、Cookie、CSRF 或 runtime.json。
- Windows 构建和办公软件验证用原生工具；跨 WSL 路径使用实际 UNC/正确参数传递。复杂命令写入任务脚本或通过参数列表传值；先排查引号、工作目录、spawn 守卫等验证脚本问题，不修改产品迁就错误夹具。

### 临时文件生命周期

- 新建大样本、额外 venv、构建目录时就明确任务归属与收尾处理，优先集中到任务自有目录；不随意散落到仓库各处。
- 大型合成库、重复任务环境、构建中间物、调试脚本和缓存，验证结束后主动核实并清理。先停止本任务已不需要的进程，保护用户仍需查看的预览及其最小运行资源。
- 删除使用逐项核实的路径清单：确认合成标记/用途、没有被跟踪的文件、没有仍需使用的进程，检查真实路径和符号链接边界。忽略列表和文件扩展名均不是删除授权。
- 保护真实 CCS/aha 资料及 sidecar、恢复副本、未知文件、最终桌面成品、主 `.venv`、源码和 Trellis 记录。未识别的对象先查明用途，不能递归清空它们所在的父目录。
- 保留必要的小型报告、指纹和可复现方法；临时大库可重建，无需长期留存。证据需要移出待清理目录时放入既定证据区并记录位置，不把整批垃圾转移到另一个隐藏目录。
- 清理后核对空间、Git 状态、必要记录和成品 SHA。报告删除类别与释放量；Git 原本有用户改动时应保留，不以“工作区干净”为由清除它们。

## 4. 失败与处理矩阵

| 情况 | 处理 |
| --- | --- |
| 只有代码/归档，没有本轮应交付的可用成品 | 继续构建、验证并交付，不能宣布整个实施结束 |
| Directory 未验收或 SQLite 不符合门禁 | 先解决原生运行与隔离环境，不放宽门禁或虚报参数 |
| 构建后又修改源码、交付副本 SHA 不同 | 重建并验证一致的成品，不单独替换包内脚本冒充已验收版本 |
| 桌面同名文件来源不明或正在使用 | 查明文件/实例归属，按 [实例契约](runtime-lifecycle-contract.md) 处理，不强制覆盖 |
| 预览链接过期、跨资源内联读取失败 | 使用当前 HTTP 服务和浏览器方式重新呈现 |
| 清理对象可能含真实资料、用户改动或仍在使用 | 保留并继续辨别；不以临时目录名代替证据 |
| 产品检查通过，后续仅修改说明文档 | 检查引用与规则一致性，不重复制造测试环境或大库 |

## 5. 正常、基础与错误场景

- 正常：功能验证后构建 OneFile，桌面副本启动和业务检查通过；保留报告，删除合成大库及任务环境，再完成提交/归档收尾。
- 基础：用户只要求解释或规则文档时，完成相应说明/写入与文档检查，不创建 EXE 和大样本。
- 错误：先宣布完成，再等用户催 EXE；留下数 GB 合成库；用忽略规则批量删除真实库；只验证源码服务却声称桌面成品通过。

## 6. 收尾必须核对的证据

1. 成品：实际路径存在，SHA 匹配，源码依据正确，从交付位置原生启动过。
2. 功能：本次变更的真实 UI/HTTP/材料链路通过；旧冻结材料保留原字节，没有带入个人数据或凭证。
3. 生命周期：重复打开复用同一服务，退出后端口/描述符按契约清理；模拟消息与物理点击验证分开记录。
4. 清理：任务临时目录已盘点，大样本和不用的额外环境已清理，必要报告与主环境保留，用户文件和既有 Git 改动未受影响。
5. 说明：用户知道成品位置和如何启动；没有把源码测试、目录版、OneFile、Excel、打印或规模证据互相冒充。

## 7. 错误与正确做法

```text
错误：代码检查 → 提交/归档 → 宣布完成 → 用户催桌面EXE → 用户催清临时库
正确：明确交付 → 实施/检查 → 构建与原生验收 → 桌面副本验证 → 清理临时文件
      → 按已有授权及工作流完成必要确认、提交/归档 → 说明成品与结果
```

时间粒度和冻结规则见 [时间合同](time-range-contract.md)；动态选择和焦点见 [组件规范](../frontend/component-guidelines.md)；过时成功与失败响应见 [状态规范](../frontend/state-management.md)。这些技术合同继续作为各自唯一来源，不在交付规范中复制一套。
