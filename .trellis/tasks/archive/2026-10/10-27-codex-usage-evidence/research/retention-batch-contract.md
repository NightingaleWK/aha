# 明细留存与报销批次契约

日期：2026-10-27。用户以“好的”同意将优化建议 O1（必要明细留存）与 O2（报销批次）纳入首版。本文细化已同意的范围，仍为待整体评审的设计，未实现产品代码。

## 1. 首版留存形态

选择不可变的历史快照，而非自动将多次读取的用量拼成一本总账。每次成功读取都保留当时可用的业务投影及其目录依据；用户可从“历史留存”选取一份，再按项目和日期筛选。当前来源与历史留存明确区分，历史条目显示读取时间和实际数据覆盖，不表示实时状态。

这样既能在源明细清理后重新打开已经留存的数据，也避免不同快照、不同请求键版本和日汇总重复相加。首版不自动跨快照补齐一个期间，未及时读到的逐次数据不能凭此恢复；用户仍可使用来源自带日汇总并人工归属。

每份快照完整保存所需业务字段：允许的 Codex 明细、Codex 日汇总、必要价格依据、结构/适配器版本和独立的会话 ID—目录元数据。原始全库配置、聊天正文、密钥和 IP 不进入留存。目录依据仅在用户本地存储，分享包不附完整路径。

## 2. 身份、去重与版本

- `usage_snapshot_id`：固定顺序的允许字段投影内容哈希；读取时间不参与内容身份。
- `metadata_snapshot_id`：允许的会话元数据规范内容哈希；按会话 ID 排序，含 cwd 与识别状态，不含完整对话。
- `capture_id`：关联上述两个不可变对象与本次来源观察。SQL 原件 SHA-256、源文件名、读取时间等属于观察证据，不冒充 SQLite 主文件哈希。
- 相同内容可以复用已保存对象并更新观察索引；重复读取和选择不同观察记录不会增加用量合计。不同内容保存为不同版本，不能覆盖此前文件。
- 明细身份为应用、来源类型及 CCS `request_id`；金额和 Token 等内容另有指纹。输入主键重复冲突拒绝导入；跨快照同键不同内容作为来源修订保留，不静默修改原快照或旧批次。
- 不按 Token、费用或同一秒时间戳相同直接去重；不同请求完全可能数值相同。旧版重建后键变化不能以“已无重复 ID”为由声称不存在消费重叠。

## 3. 日汇总和明细的边界

每次分析只消费一个明确选定的 `capture_id`。不将历史快照的明细附加到新快照的日汇总，也不以模型或日期相同为由自动替代、相减或按比例拆分。

单份来源内仍按 CCS 的明细与日汇总口径统计；来源本身有混合粒度时如实标注，不能用留存引入新的合计。对于缺少逐次明细的旧日期，用户可以人工指定完整日汇总的项目，未指定则保留未归属。

后续如要支持跨快照汇集，需要另行设计来源代际、记录键重建及完整覆盖对账；本次不加入。现有验收样例（10,852 条明细、110 条 Codex 日汇总及 2026-10-26 的 793 条/32.8928704 USD）在重复读取后仍应保持不变。

## 4. 本地存储与失败处理

使用 `%LOCALAPPDATA%\aha\aha.sqlite3` 管理项目、目录、人工归属、快照索引、批次、版本、成员及状态；不可变业务投影和 ZIP 放在同一应用数据目录的专用子目录。开发测试有独立 data-dir。没有任何数据写回 CCS / Codex。

快照投影采用版本化 JSON 和标准库 gzip，按内容指纹命名；目录元数据独立留存。写临时文件、完成校验后原子落位，最后提交索引。未提交完成的对象不显示为可用，写满、权限或校验失败有明确错误。失败读取不留下冒充成功的条目。

读取留存时校验内容哈希、内部格式和版本；损坏时不能静默以最新源替代。退出只清理临时对象和内存，项目、快照和批次持续保留。首版不自动删除历史资料，也不自动向云端备份。

## 5. 报销批次与版本

`ClaimBatch` 有稳定 UUID 和本地批次编号。`BatchRevision` 冻结所选留存快照、日期/项目条件、归属结果、项目名称、用途、参考成本、可空申请金额/币种/说明及完整记录集合。编号不称作官方账单或发票编号。

用户可从分析结果执行“创建批次并下载”，生成初始草稿版本与证据包。一个版本的内容保存后不再原地修改；修改用途、金额、筛选或数据会形成该批次的新草稿版本。旧版本、人工状态和文件保持可查，不默默应用现有目录规则重算旧版本。

每个版本的业务状态为 `draft`、`submitted`、`reimbursed`，界面为草稿、已提交、已报销。初始为草稿，后续仅按用户操作修改；允许用户纠正状态并记录变更时间。下载或成功生成文件不自动表示已经提交或收到报销款。列表显示当前版本状态，历史页保留各版本状态；新版本不继承旧版本的“已报销”。

再次下载相同版本复用原 ZIP 与原 SHA-256，不新增申请、不改变状态或重写时间。内容修改才新增版本。创建/修改/导出有服务端幂等键，重复点击、网络重试及浏览器刷新不能悄悄创建多个批次。

## 6. 重叠提醒

提醒针对其他批次，补交或重下载同一批次版本不自我报重。已提交/已报销与草稿重叠分别说明，不把另一份草稿当作已经报销。

1. 明细使用应用、来源类型和 `request_id` 检查确定的记录交集。项目、快照和金额版本不进入身份，防止改归属或重定价绕过提醒。
2. 历史日汇总缺少请求 ID，比较日期和来源/模型范围，说明为汇总范围重叠，不声称确定了同一批逐次请求。
3. 明细批次与后续日汇总批次按共同的日期、来源、模型覆盖维度检测可能重叠，避免不同粒度直接漏报。
4. 对不同请求键但会话、事件时间、模型与归一 Token 特征重合的情况，只能提示疑似重建重复，不能自动删行。仅日期相同且记录不同不报确定重复。

提示给出关联批次及重叠范围，允许查看、重导已有批次或继续创建。继续是用户当前操作，无强制阻断、自动扣减或自动“已报销”标记；采用状态/记录版本固定在提醒结果中，不改费用来源。

## 7. 证据包与重现

仍为明细 CSV、每日汇总 CSV、费用说明 HTML、导出信息 JSON 四个文件；增加批次编号和版本。清单说明所选留存快照、来源观察、归属版本、冻结成员和金额口径。快照中的私有目录不随证据包分享。

本地保存 ZIP、文件校验和与版本关联。原 ZIP 损坏或丢失时明确报错，不用当前源临时生成一个不同文件并冒充旧版本；必要时用户可创建新版本并明确标注。

付款凭证附件、规则备份恢复、额外个人用途状态和规则影响预览没有随 O1/O2 自动获批，仍留后续。

## 8. 必须通过的行为验收

- 重读、重启、源文件删除或源明细转为日汇总后，已保存快照依然可以独立恢复；多个快照不相加。
- 不同内容版本均保留；损坏和未完成写入不被当作有效历史来源。
- 同版本重下载字节及 SHA-256 相同；新版本保存旧内容和旧状态，首次导出保持草稿。
- 相同记录跨批次出现时提醒，项目规则变化不绕过提醒；明细/日汇总跨粒度给出可能重叠提示。
- 同日不相交记录不报确定重复，草稿和已报销的提示语义不同，用户可以继续而不被自动改金额。
- 本地项目、历史来源、批次及证据包在 Windows 原生程序重启后可用，异常恢复不改用户原件。
