# Codex 本地用量台账设计

状态：最终规划已于 2026-10-28 获用户批准，进入实施；实际实现与验收进度见 implement.md 和后续 verification.md。

## 1. 范围与交付

本任务是一件贯通交付：Codex 来源采集、长期台账、本地查询、报销及 Windows 本机使用共同验收。它们共享事实身份与核算口径，按阶段实施，不拆成可以各自宣布完成的模块任务。

- 目标产品版本为 v0.3.0，应用 schema 为 3，CCS 适配 schema 仍为 23；应用版本与源版本独立。
- 用户确认尚未正式使用：新建干净业务库，取消旧试用报销、占用、规则、状态、幂等、事件、ZIP 的兼容迁移。旧应用 schema1/2 不进入新业务模型。
- 历史 CCS 数据库、SQL 备份及旧留存中可恢复的 CCS 用量必须先保全；可确认无冲突者并入，冲突保留依据并待核对。历史输入保全是一次性操作，不保留旧业务库的运行期适配器。
- 仅打开时一次和手动同步；保持本机浏览器、退出按钮、隔离 data-dir 和便携 EXE。无后台定时采集、托盘、自启、云端同步或其他应用用量。
- 新台账今后生成的报销版本、占用与材料遵守冻结、独占、幂等和生命周期要求。

## 2. 架构与职责

```text
只读 CCS SQLite / SQL / 已保全的历史用量输入
  → 允许字段的有界读取、校验、暂存
  → 来源/修订/覆盖核对
  → 事实、归属、可用性和日统计一致发布到 aha.sqlite3
  → 本地 SQL 查询 / 稳定游标 / 小体积预览依据
  → 新报销冻结成员 / 流式四文件材料 / 不可变 ZIP
```

Store 继续统一持有连接、事务、关闭与文件发布边界。建议新增 `sync.py`、`ledger.py`、`queries.py`、`decimal_sql.py`；`sources.py/sql_dump.py/domain.py` 提供来源读取和逐行归一化，`analysis.py/claims.py/batches.py/evidence.py/server.py` 接入新台账。旧 capture 主查询、旧 schema 回填与旧报销协议分支应删除或重写，不能在新查询外再保留一套生产核算。

## 3. 数据模型

最终 DDL 在实施阶段按本节合同编写；所有业务身份、唯一约束与可见性必须有测试。

| 领域 | 主要表及合同 |
| --- | --- |
| 发布状态 | `settings`：当前data/classification/claim版本；一次查询绑定一个一致的版本组合 |
| 来源 | `source_profiles`、`source_epochs`、`source_rollup_observations`：来源身份、私有路径、关系与代际核对、已确认的日汇总代表请求量基线；来源前缀不能改变消费身份 |
| 同步 | `sync_runs` 及按 run 隔离的 staging：运行者/状态/时限/取消/计数/错误/发布结果；暂存 key 唯一，重复源 key 拒绝 |
| 当前事实 | `usage_records`：原 `record_key` 唯一、粒度、当前事实指针及索引用时间/日期/模型/会话字段；未核实候选与可统计事实区分 |
| 不可变内容 | `usage_versions`：同记录与内容指纹唯一，只在实际变化时新增，保存允许的原字段及归一字段；金额 TEXT |
| 溯源与别名 | `record_evidence`、`record_aliases`：事实与来源/修订候选的关联，显式确认的重建身份别名；语义相似不等于唯一身份 |
| 覆盖与核对 | `coverage_groups`、`reconciliation_cases/events`：明细/来源汇总的关系、可统计基准、候选、确认依据及不可变事件 |
| 目录与归属 | `sessions/session_metadata_versions`、项目/目录规则/内容绑定 overrides、`usage_records`内分类投影；人工覆盖优先、最长完整目录前缀其次、未归属最后 |
| 可用性与统计 | `usage_records`内可用性投影、`daily_usage_stats`及`monthly_usage_stats`：原因、所有者索引、日期/项目/模型/状态的精确统计；均可从事实和业务记录重建 |
| 报销 | `batches/revisions/revision_members/usage_claims/batch_events/idempotency`：新协议的单有效版、行式冻结成员、唯一消费占用、审计与重放；不设 legacy_review/legacy_holds |

明细继续以 app_type/data_source/request_id 建稳定 key；来源汇总继续保留 date/app_type/provider_id/model/request_model/pricing_model 的原身份。项目、来源路径、读取时间与本地源 UUID 均不参与消费 key。规则与人工归属由新库重新建立，不从试用库带入。

原始来源日汇总和本地派生日统计必须分表。计数、Token、保存成本分别保留，字段投影复用 domain。单行/汇总精确金额及大整数不能经过 REAL，也不能固定微美元后静默舍入。注册精确十进制与大整数聚合函数到 Store 各连接，返回规范字符串；自定义聚合只处理命中范围或受影响日，月年查询对完整自然月读取月派生统计，两端不完整月份读取日统计，分段互斥且按相同精确聚合合并。日/月统计和事实、分类、占用在同一事务更新，可从事实重建。

## 4. 来源同步

### 4.1 触发与资源边界

- 每次工具启动有一个自动同步身份；页面刷新、重试和多个窗口复用该运行状态，不重复发起同一启动的自动采集。手动同步可再次明确发起。
- 同一资料库同时只有一个有效同步运行者。使用持久 run 状态/租约及写事务竞争，前端 busy 不是权威锁；退出或崩溃后识别未完成运行。
- 同步名称为“完整核对来源当前允许投影、仅差异写入本地”。CCS 没有可靠 updated_at/CDC，不能靠 max(created_at)、文件时间、大小或短回扫证明无遗漏。
- 来源默认仍为当前用户 CCS 库；手动选择其他库或 SQL 是明确导入行为。来源关系无法确认时作为候选，不自动把不同来源拼成确定总账或覆盖活库当前值。

### 4.2 一次完整同步

1. 创建 run，读取当前已发布版本；查询仍使用原已发布台账。
2. 以 `mode=ro/query_only/trusted_schema=OFF` 打开来源，在同一个显式只读事务中验证 schema、分块读取三个允许表的必要投影。第一条读建立视图，所有表和分页共用该连接与事务，不复制无关应用/私有配置页，不修改源 journal_mode。
3. 读取采用 `fetchmany`，逐行归一化/指纹和本地 staging 唯一约束；替换目前 fetchall、全量 seen/sort 的生产入口。不能仅将最终写入换成 executemany 后宣称内存有界。
4. 源事务以 5 秒默认墙钟预算开始验证，源锁等待每次不超过250ms；源事务内staging等待本机writer也有短预算且检查取消，不能无限等待Python RLock；有限重试计入总预算；SQLite progress handler、块间检查与取消共同确保能终止。大源不能完成时明确失败，可主动选择 SQL 备份；不得截断后报成功。读取预算需在 DELETE/WAL 双模式实测，调整必须显式记录。
5. 允许投影仍有行数/字节限额，SQL 输入保留 128MiB 上限并仅解析字面量子集、不执行 SQL。来源导入容量与本地多年累计千万条是不同验收项。
6. 及时关闭源事务；仅为需要的 session ID 补充 Codex 目录元数据，缺失/冲突保持可见，不读正文。查询不扫描外部元数据；手动目录刷新是独立显式操作。
7. 用本地索引比较 staging 与当前事实：相同内容复用，新增写事实，变化写版本。源删除不删除本地。未变化同步只增长必要 run 摘要，不为每行写重复版本或观察日志。
8. 准备受影响归属、覆盖、可用性与日/月统计；在本地受控事务内重检发布依据，统一发布事实指针、派生数据和成功 run。失败保留原可见数据、占用和最近成功进度。

源读取采用短时一致事务而非当前整库内存 backup；事务可能在 DELETE 模式延迟源写提交，因此读锁时间是门禁。源大小增加但允许投影不变时，不应随无关表成比例复制/解析。当前整库 512MiB 限额应改为有界允许投影预算，源库文件总体积不能代替投影预算。

### 4.3 修订、空源与重建

来源 UUID 只标识本地采集配置，不能证明库未重建。活库同一已确认来源链的成功观察可推进当前事实；旧 SQL 的导入时间不能证明它比当前事实新，缺失项可补齐，不同内容成为待核对候选。

CCS 清理的汇总/删除事务是原子的，但其整轮会话重导可分批提交。一致快照只能证明已提交状态。曾有资料后明显缩水、日汇总回退、不同 key 的相同语义等信号进入来源/代际核对，保留旧事实，不从部分重建推导删除、完整覆盖或独立新消费。启发式不能保证发现所有重建，状态和文案必须如实表达。

## 5. 明细、汇总与核对

覆盖分组至少包含来源链/代际依据、日期及时区依据、app/provider/model 和规范化 request_model/pricing_model；项目不参与。源 rollup date 原样保留；北京时间是既有核算约定，不假称备份携带了已验证时区。

| 情况 | 统计与申请行为 |
| --- | --- |
| 只有明细 | 统计已观察到的明细，显示覆盖依据；不保证这一天绝对完整 |
| 只有源汇总 | 按来源粒度统计，可整条人工归属；不能拆成小时、会话或请求 |
| 明细与汇总有可信覆盖依据 | 只采用一个核算基准，另一份保留为核对依据 |
| 仅数值匹配或成员/代际/时区不明 | 标记待核对，双方分别可查且不可相加，不输出冒充完整的唯一总额，不进入可报销用量 |
| 部分覆盖或费用差异 | 保留双方和缺口，不造差额明细、不按比例分摊；核对完成前阻断歧义申请 |

计数/Token 相同不能证明请求成员相同；上游浮点汇总尾差、清理前补价与 effective filter 差异分别记录，不自行引入新的 proxy 去重口径或改写逐条金额。

核对操作以组/候选为主体，用户可明确采用明细基准、完整汇总基准、确认修订或来源关系，记录原因与 expected generation。部分明细被采用时仍注明只覆盖已存部分。选择基准不删除原始依据、不释放占用；与现有新台账报销冲突时须先按正常业务纠错。语义相同的新 key 只能成为重建候选，不能自动合并真实不同请求。

## 6. 本地查询与一致发布

- 列表按 `(project_id,event_time,record_key)`、`(event_time,record_key)` 和真实谓词设计索引，另为 session/覆盖/semantic/claim 查询建立必要索引；以 EXPLAIN 验证，不机械堆索引。
- 使用稳定游标前后翻页，默认 50、最大 200 行。游标绑定筛选和 data/classification/claim 版本，版本改变要求刷新；不使用深 OFFSET，不把所有行缓存后切片。
- 全局可用性建立派生索引，相关所有权通过 record/scope/semantic 索引检索，不能读取全部 claims 建 Python 字典。日/月统计同时维护全部、可用、排除及歧义说明；所有者解释只展开当前页/受影响组。
- 修改目标批次时的自身占用豁免单独查询，按现有 claims 语义对照测试；不能把自己的全部成员简单加回全局可用统计。
- 归属规则/人工覆盖/目录证据、来源修订/覆盖确认以及占用变化均使相应范围的派生数据失效或更新；不能只在同步时更新统计。
- 预览只保存条件、摘要和版本依据。新建/修订冻结完整选择，不以当前页为成员；事实/归属/claim 变化后失效。幂等重放优先于临时预览重检。
- Store 统一管理序列化 writer 与短时读取连接；外部读取和大文件生成不长期持有Application/Store全局锁；staging只在有界短事务批写，源读锁不能被本机写锁无限延长。事务中完成必要权威校验和可见性提交。

### 实施阶段的性能与来源细化

2026-10-28百万条预跑证据：只有tuple游标条件时SQLite仍从日期起点seek，已增加游标时间标量上下界；全期日统计的GROUP BY临时排序和逐指标Python回调已改为单次精确分组聚合。物理1m分页P95≤6.7ms，但全期进程冷约1.62s超目标，因此增加月派生层，保留事实、精度与原验收门槛；最终仍须实测。

同源等量更换key时，语义相同旧key已不在完整staging才产生重建候选；本轮仍并存的新旧key按真实独立请求保留。已观察rollup行数减少或同源同key的request_count下降也进入needs_review；费用变化而代表请求量未下降仍走正常修订。确认新来源基线与选择事实版本是分别记录的核对动作，旧事实及原材料保留。

## 7. 报销与材料（仅新台账）

草稿立即占用，只有一个有效版本；仅有效草稿可修订，已提交带原因撤回，已报销纠错通过作废再新建，作废为终态并仅释放自身占用。状态、幂等和事件使用干净 schema 实现，不接续旧试用记录。

冻结成员以行式 `revision_members` 引用不可变事实/归属版本，manifest 使用新协议版本，明确 ledger/selection 和来源依据，不伪造单一 capture。四文件名称、CSV BOM/公式保护、HTML 转义、精确成本/人工金额分离和隐私要求保留。

在写事务外分批冻结候选并流式构建临时 CSV、manifest 和 ZIP；最终事务重新核对 data/classification/claim/generation、冲突和幂等，登记不可变材料、有效版本与占用。失效必须明确失败，不能缩小选择后沿用人工金额。CSV、成员 JSON、ZIP、校验和下载全链路流式处理，不能只优化 CSV。

旧试用 ZIP 不导入新库；新台账 ZIP 重下返回原字节。当前事实修订通过冻结成员索引提示差异，不改历史包、不释放占用。

## 8. 页面与接口合同

- 主页面默认“本地台账”，项目/日期/可用范围筛选直接查询 SQLite；旧 capture 选择器不再承担查询主体。历史来源进入来源/核对入口。
- 先展示可查询的本地数据，再执行本次启动的自动同步。同步失败持续显示错误、上次成功时间及仍可查询的旧数据。
- 同步与只读查询使用不同忙状态；只禁重复同步及必要变更，避免整页被全局 busy 锁住。退出取消未完成工作并释放资源；保留现有关闭标签不自动杀进程的方式，不增加关闭后的定时采集。
- `POST /api/sync` 以来源、startup/manual、启动身份与请求 key 发起/复用一次运行；`GET /api/sync/{id}` 只返回进度，不触发采集。轮询仅持续到本次有限运行结束。
- 来源设置和 SQL 导入共用同一校验/暂存/发布管线。默认活库、显式其他库、旧备份的可信新旧关系分开，不静默切换默认来源。
- `POST /api/analysis` 以本地筛选和版本生成小体积预览；`GET /api/analysis/{id}/details` 以 cursor/size 返回分页。新分析不需要 capture_id。
- 核对动作以 case ID、选定候选/基准、原因、expected generation、幂等 key 为输入，只能作用于该 case 的合法候选。
- 报销路由保留用户操作能力，载荷改为新预览/冻结依据；新建、目标修订、自身豁免和过期弹窗仍严格区分。
- 继续本机认证、端口 Cookie、Host/Origin/CSRF、允许字段、内置资源、简体中文和现有可读字号。内部协议/代际编号不进入普通产品流程或分享包。

## 9. 一次性保全、重建与回退

1. 实施前重新盘点 `%LOCALAPPDATA%\\aha`，确认旧进程退出，列明源资料保护清单和可清理的 aha 试用文件。2026-10-28 规划仅检查了目录：12 个文件、56,261,345 字节，含 6 个 usage、3 个 metadata 压缩对象、库/库备份和 1 个 ZIP；未读取业务内容、未清理。
2. 历史 CCS 活库/数据库/SQL 原件保持原位置；保护其 SQLite sidecar。对试用目录做一次性可逆保全，独立目录存放且校验。原活库可继续自然变化，不以其文件哈希变化误判 aha 写入。
3. 旧 usage 对象按内容哈希、格式和 domain 规则验证，提取允许的 CCS 用量为独立历史导入输入；可用目录依据可保全为来源线索，旧项目/人工归属不继承。这个工具是一次性资料处理，不读取/迁移旧报销业务。
4. 在隔离副本完成提取、清理和新库导入演练后，才按用户已授权的范围清理实际试用文件。精确允许清单包含旧应用库及匹配 sidecar、已保全对象、试用 packages/旧应用 backups；未知文件、任何 CCS 原件和未保全输入不删除。禁用父目录递归删除和全局扩展名清理。
5. 初始化干净 schema3，重新配置项目规则。无冲突历史用量并入，歧义转核对；对提取前后唯一身份、版本、费用/Token 和覆盖状态逐项核对，不能因“清空试用数据”丢失历史消费。
6. 新产品仅识别空库和 schema3；遇 schema1/2 明确提示先进行受控试用重建，不静默迁移或丢弃。旧程序不能打开新 schema；不设计旧 writer 共存。
7. 失败时停止重建，保留原输入和一次性保全目录，可恢复原试用资料；新旧程序均须退出后恢复。新成品单独命名，旧 EXE 不覆盖。

## 10. 性能验收与运行时门禁

性能数字为待评审验收目标，不是已测结果。固定 seed，100 万/1000 万事实，跨度 5 年、至少 100 项目/20 模型、50% 集中单项目的倾斜、未归属、1% 修订、30% 占用及明确构造的覆盖冲突。来源窗口独立固定，不向 CCS 写入合成资料。

| 场景 | 验收目标 |
| --- | --- |
| 50 行第一页/中间/深位置游标，单/全项目，全部/可用 | 热态 P95：100 万 ≤300ms、1000 万 ≤500ms；进程冷启动首次查询 ≤1.5s |
| 项目月、年与全项目月统计 | 热态 P95 ≤1s；执行计划与访问范围证明读取派生统计 |
| 不变来源重复同步 100 次 | 新事实/内容修订增加为 0，只允许必要 run 元数据/staging 开销 |
| 固定来源窗口，本地从 100 万增至 1000 万 | 同步耗时比目标 ≤1.5，分别记录读取/比对/派生/发布 |
| 同步新增 1 万、修订 1000 行时查询 | 前台查询 P95 ≤1s；未发布内容不可见，失败不改成功进度 |
| 导出 10 万/100 万选择，含 manifest、ZIP、下载 | 额外峰值 RSS ≤128MiB，完整成员/金额/文件哈希对账 |
| 相同限定查询在两种本地规模 | 额外峰值 RSS 差 ≤64MiB；分别记录库、索引、修订、WAL、证据材料大小 |

查询预热 10 次、至少测量 100 次，记录 P50/P95/max；进程冷不等于系统磁盘冷，不清宿主全局缓存。源读取锁时间、首次导入、大范围归属重算及 SQL 输入预算独立报告，不与热查询混为同一指标。未达门槛必须优化/复测或返回规划，不得仅用“SQLite 能放下”交付。

在采用多连接 WAL 前，Linux 与 Windows 均验证实际 SQLite 含 WAL-reset 修复（3.51.3+ 或核实过的回补分支），统一 writer/checkpoint 与短读连接；主机只读探测的 SQLite3.46.1 不可当作已修复基线。必要时仅调整任务隔离的构建运行时并采集许可证/版本，不改全局环境或 CCS。实现前完成精确聚合、流式冻结/导出及源 DELETE/WAL 锁预算的小型技术验证，失败返回设计，不降低金额精度、放松防重或偷偷关闭保护。
