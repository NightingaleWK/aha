# 换机后的记录与项目关联连续性

## 目标

让 aha 可靠回答“每个项目实际消费了多少”，并能从项目合计追溯每条消费、作为向公司申请报销的证据。永久记住每条消费是基础，把记录正确、稳定地分到对应项目是核心能力；换机、目录扫描、备份和恢复均围绕这一闭环服务。

本任务实施目标包括恢复可证明的旧关联、持久记录归属、便捷的待归属处理、项目统计与材料的一致性，以及 Windows 桌面成品。用户在最终规划展示后已回复“开始实施”，完整范围已批准。完成本机交付后，用户又明确授权现在正式发版、合并main、git push、收尾及归档，并确认本人功能实测无问题；新增发布验收沿用同一任务推进。

## 背景与证据

用户已在旧电脑维护项目与记录，新电脑缺少旧 Codex 数据后观察到历史记录无法关联项目。2026-11-12 用户回复“按你说的做”，确认默认保留历史归属的推荐方案；随后明确行动方针应围绕记住消费、将每条记录归到项目、统计项目费用并形成报销证据。本次不再重复询问该产品政策。

2026-11-12 11:31 北京时间原生只读核验：5 个 aha 项目保留；347 个旧会话当前 missing，影响 38,978 条历史明细，但都留存唯一有效历史目录。其中 297 会话/37,165 明细可按现有目录规则重新关联项目；50 会话/1,813 明细仅能恢复目录，仍待指派。当前另有 1,625 条新机明细有目录但无匹配项目规则，不属于丢失历史依据。聚合、时间线与限制以 [诊断记录](research/association-findings.md) 为准。

直接代码依据：`src/aha/projects.py:88` 证明项目直接来自本地库；`src/aha/ledger.py:244` 以当前 sessions 重算归属；`src/aha/sync.py:335` 防止有效 matched 因缺文件被清掉，但没有回填已经 missing 的历史；`src/aha/projects.py:235` 的整会话分配仅展开当前记录；`src/aha/queries.py:890` 不提供历史失效目录候选。旧刷新实现与 09:34 missing 版本记录解释当前脱节；前次只验原样保留未覆盖恢复缺口。

## 需求与可观察验收

| ID | 需求 | 验收标准 |
| --- | --- | --- |
| R1/A1 | 解释真实问题和可恢复范围 | 区分项目存续、当前目录、历史依据和业务归属；数量与只读证据一致，不能把预期恢复写成已经恢复 |
| R2/A2 | 无旧机日志也能保留/重建可证明的关联 | 唯一历史证据可预览并批量采用；多候选/无依据/明确否决留待核对，不按名称或时间猜测 |
| R3/A3 | 复用同一 aha 项目接续不同机器目录 | 项目 UUID 延续；旧目录不因本机不可访问而失效，新目录可附加到同项目，不强制重建项目或复制 Codex 全量资料 |
| R4/A4 | 每条记录有稳定、可解释的项目归属 | 有效归属持久保存；目录/会话用于辅助批量分配，不能是每次必须重新获得的前提；整会话绑定覆盖后续新增记录，逐条例外仍可维护 |
| R5/A5 | 修改目录默认保留已确认历史 | 新规则用于尚未确认归属的新会话；已有会话延续原关系；追溯修正须单独预览会话/记录/金额影响并明确应用 |
| R6/A6 | 兼容核算、占用、材料与完整恢复 | 关联操作不修改消费身份/成本/Token、原 coverage/suppressed、claims 或冻结原包；统计/预览一致，旧完整备份仍有明确可恢复路径 |
| R7/A7 | 先形成可审阅规划，再按最终范围实施 | 诊断、需求、设计、执行计划和上下文齐备，无阻塞产品待决策；最终审阅前保持 planning，不把只读推演写成修复通过 |
| R8/A8 | 未归属是必须方便处理的工作清单 | 按原因/目录/会话/时间聚合，支持按筛选全量选择而非只选当前页；可批量预览分配、逐条例外和纠正；无依据不猜测，未归属未处理完不冒称关联工作完成 |
| R9/A9 | 项目金额与逐笔证据一致、总量守恒 | 同时间/粒度/可用性口径下，各项目与未归属互斥且合计等于全部可统计用量；项目摘要、明细、日/月统计与新材料一致；披露同期未归属，不将其混入确定项目或无条件阻断其他已确认项目报销 |
| R10/A10 | 完成真实资料修复和可直接用的 Windows 交付 | 先完整备份并在一致副本验收，再对当次有依据的真实记录恢复；交付最终源码一致的桌面单文件 aha.exe、原生验证与回退说明；不把规划或测试副本当真实修复 |
| R11/A11 | 按最新授权发布并完成Git收尾 | 核对v0.4.1以来累计What’s New，发布PR统一升号，固定merge SHA与实际候选，完成适用验收并核对正式公开资产；最终main合并/推送、正式EXE交付、发布资源清理和任务归档/日志均有实证 |

以上为本任务最终要求，现已实施并完成源码、原生 EXE、真实副本与真实台账恢复检查；逐项证据以 [验收记录](verification.md) 为准。真实台账中证据充分的 37,165 条明细已恢复项目归属，3,438 条明细和 110 行计入统计的历史日汇总仍待人工确认，不能宣称全部消费已经归属。具体数据与兼容合同见 [设计](design.md)，实施次序与验收矩阵见 [执行计划](implement.md)。

## 范围外

- 最初实施包含 R10 的保全、真实资料修复和桌面成品。用户在本机验收后追加R11，现已授权远端推送、main合并、公开发布、提交/归档；不再把先前的授权边界当成当前阻塞。
- 不依赖已格式化旧电脑，不读取聊天正文/凭据，不从日汇总伪造明细或项目拆分。
- 不实现多个独立业务库双向合并或跨库报销协调；不自动把通用工作目录全归到一个项目。
- 不把项目名称相似或不同平台的目录字符串相似当成可靠项目身份。
