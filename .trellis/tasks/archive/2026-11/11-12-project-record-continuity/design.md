# 逐笔消费归属、项目统计与换机连续性设计

状态：最终规划已审阅，用户于 2026-11-12 明确批准开始实施。用户已确认保留历史归属，并明确程序的主目标是记住消费、分配到项目、统计费用并形成公司报销证据。本文是实施合同，不能当成已完成的产品行为。

## 0. 以消费与项目为中心

主流程为“消费留存 → 逐笔归属 → 项目核算 → 冻结报销证据”。每条可统计消费最终只属于一个项目，归属能解释来源和修改；没有充分依据时保留为明确的待办，不能靠猜测凑齐或在完成报告中略过。目录发现率不是业务验收终点。

同一时间、粒度和可用性口径下，所有项目已归属量 + 未归属量 = 全部可统计量，金额和 Token 同样守恒，任何消费不重复。当前已 suppressed 的日汇总不参与相加。项目合计可下钻到成员，明细、日/月汇总与材料使用同一成员选择。

目录/会话用于识别、建议和批量选择；已确认的逐条关系保存在 aha 中，不能只在查询时临时推导。换机、源库消失、目录停用均不撤销已确认归属。

## 1. 边界与复用

当前机制与数据证据见 [研究记录](research/association-findings.md)。复用现有 `projects.id`、一项目多目录、规范路径/最长目录匹配、记录级 overrides、元数据版本、核对事件、精确日/月统计和完整备份。不要新建一套以 Codex 项目为主键的项目表，也不要要求找回旧日志。

分两步交付，不能以长期模型实施较大为由跳过当前数据恢复：

1. 恢复已经 missing、但存在有效历史版本的目录依据；同一基线输出可审核的项目重建预览。
2. 建立持久的逐条关系和持续会话绑定，完成待归属清单、历史影响预览、项目统计/证据链及无损升级。同一任务按依赖串行实施，最终作一次完整交付，不先交付一个只恢复目录而没有业务闭环的版本。

## 2. 当前历史恢复

### 选择与限制

- 只检查 detail 对应的 missing/未知目录会话；当前有效目录、有效人工记录归属和已处理的矛盾候选优先，不被历史回填覆盖。
- 对 `session_metadata_versions` 的 matched 绝对目录，按现有平台路径规则去重；仅有一个唯一候选且没有明确否决/相反证据的项进入可恢复组。
- 多个不同历史目录、无有效历史、版本哈希不一致或记录/目录核对仍未解决时，进入需核对组，不能简单“取最后一个 matched”。
- 唯一历史目录仍未命中项目规则时，只恢复目录线索，保留未归属；允许按目录或会话批量指派。日汇总没有会话依据，维持整条人工归属，不拆分或按比例分配。
- 跨 Windows / WSL、不同用户名、不同盘符不靠路径字符串相似度自动推定同项目。用户将真实目录明确绑定同一 aha 项目后才能使用。

### 预览和应用

拟增加只读恢复预览和原子应用入口，挂在“项目管理 → 关联检查”，默认不在启动/同步中静默修复真实业务资料。名称和具体路由在实施时遵循既有 HTTP 风格。

预览给出项目分组、会话/物理明细数、时间范围、金额影响，以及“可恢复项目关联 / 仅可恢复目录 / 多候选或缺依据”。显示“按当前项目规则重建”，不冒称精确恢复从未单独保存的历史项目快照。

预览身份绑定 data/classification/claim 三修订号、候选 metadata_version_id + content_hash、当前有效元数据 hash 及规则摘要。提交在一个有界写事务中重检；同步、规则、人工分配或核对变化后返回失效，让用户重新预览，不部分套用旧方案。

复用现有 directory 候选采用逻辑和 reconciliation_events 保存历史版本依据、操作理由与结果；批量动作最多 1,000 会话，服务端限制与界面一致。预览不写 case；应用时生成/采用及批量审核必须在同一事务内完成，不能逐会话多事务留下半恢复状态。幂等重试复用既有机制；旧 missing 历史版本保留，不删除证据。

只更新有效目录/归属及受影响派生统计。消费 key、usage_versions、原始成本和 Token、claims、suppressed/coverage 决策、批次及原包不改。重分类和日/月统计复用 ledger 共享入口，在同一事务更新；成功后统一失效页面分析/保存身份，再按当前筛选重查。

恢复候选研究与夹具复用现有 schema3 的版本/核对结构；最终成品与下节的持久关系及迁移一起验收。真实原库应用前须以一致副本验证并创建新的完整备份；规划阶段不执行这些写入。

## 3. 持久的逐笔关系与批量辅助

概念关系：

```text
aha 项目（稳定 UUID）
  ├─ 旧目录、新目录、Windows/WSL 目录规则
  ├─ 已确认的逐条消费归属（主要关系，有依据与修订）
  └─ 会话默认归属（批量辅助，并覆盖后续新增记录）

本机 Codex 观测 → 新线索或冲突候选 → 接受后补充依据
```

新增记录关系 `record_project_links`（名称可随模块约定调整），以 canonical record_key 为唯一键，外键指向已存消费和 aha 项目，保存关联依据类型、依据引用/快照、generation 与时间。持久保存目录规则/历史恢复/会话默认产生且已接受的关系；usage_records.project_id 仍是查询和日/月统计的快速投影，不能反过来成为唯一可被刷新覆盖的依据。既有有效记录级 overrides 继续是显式人工例外，不改变其内容指纹校验合同。

补充 `session_project_bindings`，记录 session_id、project_id、依据与 generation。会话默认用于同会话后续新消费；它不能代替逐条关系，也不能抹去逐条例外。

一般重分类优先级：有效记录 override → 已接受的持久记录关系 → 对新成员适用的会话默认/唯一目录规则 → 未归属。初次采用规则或会话默认时即保存逐条关系。以后同步、扫描或保存规则不得绕过已接受关系；只有显式历史归属操作可改这些关系并记录审核事件。无效内容指纹的人工 override 继续按现有规则重新判断，来源事实修订仍走核对，不能用稳定关系跳过费用版本确认。

关系改变有可追溯事件：操作身份、记录/会话范围、旧/新项目、依据、理由、时间与修订。复用核对采用和幂等逻辑；新增表结构时归属事件纳入同一 schema 与完整备份。按 canonical key 处理已确认别名合并，不能靠来源/设备 ID 复制一条消费或产生两份项目费用。

“按整个会话分配”明确提供持续会话绑定。旧版本的逐条 overrides 不自动推断成持续绑定，因为库里没有保留当时是否勾选“整个会话”的用户意图。解除记录例外与解除会话绑定分别表达，不能沿用 null 一个含义覆盖两类动作。

已有 aha 项目改名保留 UUID。换机时旧目录保留为历史依据，新目录追加到同项目；只在新机存在的目录不重新创建一份旧项目。有效历史依据与“本机本次扫描没找到”分别显示，不能把本机可访问性作为项目是否有效的判断。

不引入长期双机业务库合并。对于旧目录被新用途复用，可停止该规则用于新会话识别，但不撤销旧会话已确认归属；新项目重新绑定相同目录需要明确解除/调整旧规则，并展示冲突与影响。历史环境未知时标未知，不根据当前安装标识伪造旧设备身份。

## 4. 已确认的目录规则与历史政策

用户已确认 D1：默认保留已确认历史归属，新规则用于尚无确认归属的新会话。已有会话的后续用量继续继承原默认关系，但允许逐条例外。需要修正历史时，单独选择“重新归属历史”，先预览受影响会话/记录/金额，再显式应用。原来未归属但有唯一目录证据的历史可在同一预览中批量补关联。

保存新目录规则与追溯修改为不同意图；界面可连续完成规则设置及历史预览，避免用户重复选择，但不能把普通保存隐式升级为历史修改。用户不需要为了保住历史而永远保留当前已不用的目录规则。

## 5. 持久结构与完整恢复兼容

当前 schema3 没有新版本迁移分支，完整恢复严格按当前表/索引/DDL 校验。本任务新增持久关系，正式引入新应用 schema（计划为 4）与 schema3 的无损受控迁移；产品发布版本仍由发布 PR 统一管理。不可在相同 schema3 下偷偷增加表、导致旧完整备份被误报损坏。

迁移先保全原库，事务内新增结构、迁移有充分依据的关系并校验外键、数量和统计。当前已有效的目录规则归属逐条种入关系；现有记录 overrides 保持原指纹语义，不从其数量推断旧用户是否勾选整会话。未知/已失效部分不在迁移时猜测，留给恢复预览。迁移前后原有归属、事实数量、当前费用与日/月统计保持，不改既有消费身份、历史版本、包字节、原备份。失败回滚，旧版面对新 schema 明确拒绝打开。不能复用“试用资料重建”的删除流程。

备份按 manifest 中的 store_schema_version 选择对应权威结构定义；恢复旧 schema3 先独立校验，再在新目录受控迁移。恢复包本身不改，格式能表达新 store schema 时不为此随意改容器协议。迁移后的绑定/依据/审核事件完整进入新备份；本机安装身份仍按恢复合同排除。

schema1/2 与未知版本保持拒绝；支持的 schema3 升级不能再误走试用资料重建错误。修订/材料中的应用库版本读取权威 schema 常量，内部用量投影仍为 23；历史冻结说明和原 ZIP 不回写。

## 6. 界面与异步状态

项目卡片以项目费用、记录数、期间和归属依据概况为主，目录放在维护入口。待归属清单分“历史依据可恢复”“有目录但未绑项目”“无依据/冲突”，可按目录、会话、时间筛选、批量确认并下钻到逐条记录；支持明确选择筛选结果而不是误把当前页当全部。服务端使用有界流式/临时关系选择；超限明确提示分批，不将全历史成员读成 Python/前端数组。

待归属进度分别呈现物理明细数、日汇总行数及其代表请求量，避免用代表数量冒充存在的逐笔证据；展示待归属金额，帮助优先处理影响较大的集合。无证据的记录保留待办，不因扫描结束宣称全部归属完成。

项目结果只计入确定属于该项目的成员；同期间未归属在页面和新材料中作独立说明，不算入该项目，也不无条件阻断其他已确认项目报销。现有 unassigned_count 已有期间统计基础，补明确粒度/金额与归属覆盖说明；页面可显示待归属金额，分享材料只披露覆盖与待归属数量，不带其他项目、完整目录或未归属明细。归属覆盖与时间/业务核对完整性分开表达，不能把“所选成员核算完整”误称为“所有项目消费已经分配完”。这类说明与预览一同冻结；旧原包保持字节，旧版本没有该信息时保留未知。

新增预览/提交复用 run/api、动态项目 select 与 AhaForms.sync；关闭弹窗/切项目/选择变化后，旧成功和旧异常均不提交。审核完成失效分析和旧保存身份；断连重试保持幂等。键盘、焦点、错误恢复、长名称和窄窗口按前端规范验收。

## 7. 回退与验收边界

恢复与持续归属的验收矩阵见 [执行计划](implement.md)。恢复可用预览前保全的完整备份回退到新资料目录，不在线覆盖当前业务库、不只回滚目录字段却保留不匹配的统计。

本轮只进行了原生只读诊断与规则推演，没有运行恢复、迁移、产品测试、浏览器、Directory/OneFile 或真实库写入验收。不得将预期数量写成恢复成功结果。
