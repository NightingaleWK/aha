## 已发现并修复

1. **P1：元数据截断被误当作不存在。** 全筛选 `reclassify` 会把未纳入前 20,000 会话的既有归属清成未归属；同类问题还会让 `assign + reason=missing` 错选已有 matched 目录的记录。使用缩小资源上限的两个真实合成会话分别复现。现读取和预览共用 `_require_complete_metadata`：目录/原因依赖未完整时安全拒绝，明确具体会话/记录仍可聚焦处理，纯人工的项目/日期选择继续。status 不将未检查会话塞进 missing 分组，完整待归属总量保留；分页补查当前页元数据。UI 区分会话依据只检查部分与仅前 1,000 组展示。
2. **P2：当前预览覆盖已变化却返回旧报销版本。** 当项目成员、金额、用途未变，只有同期未归属覆盖变化时，原 no-op 判定丢掉新说明。现在原 business_hash 相等之外比较完整规范化 `assignment_coverage`，旧缺字段按 null；不改成员/业务哈希算法。回归证明新覆盖形成 v2、真正无变化仍复用、重试幂等、frozen 继续沿用旧依据、旧 ZIP 不变。
3. **P2：别名合并丢失唯一已知项目。** canonical 未归属而候选已分配项目时，旧逻辑只 suppress 候选，导致已知项目从合计中消失。core 根据复核报告新增 identity_confirmation 关系及审核事件；不复制候选的内容指纹人工覆盖，仍保留财务修订核对/claims/原包，双方非空项目冲突仍阻断。来源标签及中文界面明确为身份核对，避免冒称目录匹配。
4. **P2：结构化坏游标与不适用会话选项。** base64 编码的 `{}` / `{"x":1}` 原会抛 KeyError，非分配动作的 `bind_sessions=true` 原会在应用时触发 SQL 非空约束。core 已分别在读取/请求边界校验，返回安全客户端错误而非 500/晚期写入失败。
5. **P2：新建项目成功后的刷新失败会导致重复创建。** 使用真实 app.js 状态 harness 复现成功 POST 后归属刷新断线，再次保存仍 POST 新项目。现成功响应即保存返回项目 ID，立即使旧分析/保存身份与关联预览失效；刷新失败明确项目已保存，重试更新同一项目。回归分别覆盖项目刷新与归属刷新失败。
