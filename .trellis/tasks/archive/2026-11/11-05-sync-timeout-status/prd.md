# 修复同步超时与失败状态提示

## 目标

恢复 Windows aha 从 CC Switch 同步当前规模用量的正常使用；同步失败时让用户明确知道页面显示的是已保存的本地资料，并单独提供上次成功时间。交付与最终源码一致、从实际桌面验证过的单文件 EXE。

## 已确认事实

- 2026-11-05 用户先授权只读诊断，随后要求开始修复，并明确同意创建 Trellis 任务、进入规划；最终方案已获用户“开始实施”确认。
- 当前源码为 `main` / `a635ae3`，工作树在任务创建前干净，截图中产品版本为 0.4.0。
- 本机 CC Switch v4.0.25 的外部 SQLite 结构版本为 24，必要用量字段通过当前适配器检查；本次失败不是结构拒绝。
- 当日四次真实同步均约 5.5 秒后以 `source_busy` 失败；最近成功时间为北京时间 2026-11-03 10:47，该次读取和暂存耗时约 4.15 秒。
- 原生 Windows 源码隔离诊断：29,106 条明细、117 条日汇总、9 条相关价格的只读扫描耗时 911 ms；生产暂存逻辑在 5 秒预算下失败，实验放宽预算后在 5,377 ms 完成。该实验使用 Python 3.15 / SQLite 3.53.4，不冒充原桌面 EXE 验收；临时投影及暂存库已删除。
- `src/aha/sources.py:28` 将源读取预算设为 5 秒；`src/aha/sync.py:732` 将同一预算用于规范化、指纹计算及本地暂存。`src/aha/web/app.js:223` 只要存在历史成功时间就显示“已同步”，未优先反映失败。

## 需求

### R1：可靠同步且保持来源只读边界

- 源库短时一致读取与本地处理解耦；本地处理超过 5 秒不得被误判为源读取超时。
- 保持来源只读、必要字段白名单、23/24 兼容、同一快照、一致指纹和现有行数/字节上限。
- 保持真正的源锁等待/源读取超时、取消及本地争用有界；本地处理不再延长 CC Switch DELETE 读事务。
- 保持重复导入、自然缩水/修订核对、精确金额、事实身份及旧材料字节不变。

### R2：失败状态准确表达资料时效

- 最近同步失败时，状态卡优先显示“同步失败”，保留错误原因和上次成功时间。
- 有旧资料时明确提示“当前显示已保存的本地数据”，独立展示上次成功时间；待核对同步可能已经保存新增事实，不能声称当前资料等于上次成功快照。尚未成功同步时使用对应表述，不把来源失败说明成当天实际零用量。
- 重试、同步中、需要核对、成功及刷新后的状态正确；旧台账仍可查询，成功后恢复正常状态。

### R3：验证、成品与维护记录

- 补充有意义的后端并发/回滚、HTTP 及页面状态回归，完成相关质量检查和原生 Windows 实际页面验证。
- 在独立合成资料上验证至少 3 万条当前规模明细，以及超过旧限时的本地处理，记录真实耗时和执行环境。
- 按既有脚本先验证 Directory，再构建验证 OneFile；确认实际桌面后交付 `aha.exe`，从该副本再次启动验证。构建运行时变化时执行合同要求的追加专项。
- 编写中文 What’s New 片段、更新受影响规范、保存必要证据；清理本任务自有临时库、构建中间物和额外环境。

## 验收标准

- AC1 → R1：源读取在预算内完成而本地处理超过旧 5 秒预算时，同步成功；至少 3 万条合成明细的原生结果正确。
- AC2 → R1：独立源连接能在本地慢暂存期间成功提交；DELETE/WAL 一致性、真正源超时、取消、锁等待均不退化。
- AC3 → R1：读取/临时文件/暂存/取消失败不发布部分结果，不推进成功时间，不改旧事实或原包；临时文件关闭并清理。本地库可写时清本轮staging并记失败；争用阻止持久清理时有界返回原错误，同一进程在取得写锁后重试前精确回收，跨重启沿用120秒租约并回收过期stage/pricing，保护其他有效运行。
- AC4 → R1：23/24、重复同步、金额/Token、缩水/修订核对和旧冻结材料兼容回归通过。
- AC5 → R2：失败有/无历史、重试中、待核对、恢复成功与刷新场景均显示正确状态；失败后的零条统计不被呈现为来源已更新。
- AC6 → R3：适用自动检查及真实浏览器验证通过，Directory/OneFile 分别原生验收；桌面副本 SHA256 匹配且实际启动验证。
- AC7 → R3：必要证据、中文片段、规范和清理完成；交付后给出发版评估及仍需用户决定的公开发布范围。
