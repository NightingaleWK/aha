# 目录整体归属设计

状态：用户于2026-11-13批准最终规划，实施中；不是已完成验收的行为。需求与验收以 [PRD](prd.md) 为准，拥有者证据见 [研究依据](research/findings.md)。

## 1. 业务模型与兼容边界

`aha 项目 UUID → 一组目录 → 目录内全部有依据消费` 是新常用模型。逐笔关系继续存储成员身份和审核证据，但不再允许已明确纳管的目录被旧 overrides／session_project_bindings 拆散。首次明确确认同时采用目录整体模型并统一历史，此前原库仍沿旧合同运行。

不在启动或数据库打开时自动转换已有项目。原有项目配置保持，项目卡提供“确认目录关联”；新建／编辑目录时自动进入同一预览。用户只改名称且目录和模式均无变化时可保存元信息，不重迁历史。

原人工关系不得直接删除掉全部历史证据：对被本次绑定覆盖的记录记录旧项目、依据、操作身份和新项目；失效的相反 override 可受控清除，旧审计事件保留。无目录日汇总及未纳管目录继续兼容原模型，其处理入口在高级区。

## 2. 拥有者与复用

- `projects.py`：目录规范化、草稿配置、目标项目和跨项目目录转移的验证。
- `project_links.py`：共享有效目录／权威归属判定、持久关系与审核、旧例外清理。纯 classify 与 ledger 必须调用同一规则，不保留两套优先级。
- `associations.py`：复用有界元数据、候选流式选择、精确聚合、预览缓存、修订／摘要校验及幂等应用基础；项目保存的事务编排由项目领域函数拥有，不套用按整会话展开。
- `ledger.py`：事实归属投影、受影响 scope 及日／月统计；`sync.py`：元数据观测和差异发布触发归属更新。
- `storage.py`：新增薄门面；`server.py`：Cookie／Host／Origin／CSRF和载荷边界；`web/app.js/index.html/style.css`：目录选择、单一影响确认和结果反馈。
- 不在前端拼接全部 record keys、不复制金额计算、不新建项目或消费的影子账本；只有职责确有必要时拆一个小的领域模块，避免继续把整个流程塞入 Store。

## 3. 持久策略与目录所有权

计划继续使用 schema4 既有表：`projects.directories_json` 保存唯一目录所有权；`settings` 中增加版本化的 `directory_assignment_policy`（version=1，已明确确认纳管的项目 UUID集合）。`record_project_links.basis/basis_json` 保存 directory_binding、已采用目录、项目／规则依据；已有审计表记录本次整体调整。没有新表、索引或结构变化，不借用 schema 数字伪装 DDL 变动。

配置读取验证策略版本和项目引用；未知／损坏策略拒绝相应写入，不静默降级后重分费用。完整备份原样保留新设置和关系证据，恢复到新目录后仍能自动匹配；原 schema3／4 备份无该设置时作为未纳管旧状态接续，不自动推断。

目录用现有 canonical_path 和 _contains：Linux 大小写敏感，Windows盘符／UNC遵循现有规范；显式列出旧／新路径作为同一项目的独立别名，不访问路径本机存在性来决定历史身份。

同项目父子目录去重统计。同一规范目录从另一项目转移，预览包含被移除的旧目录所有权；确认原子更新两边项目。不同项目存在严格父子重叠时拒绝确认，说明冲突的两个目录和项目，要求在目录层明确范围；不扩大到无关兄弟目录，不保留不可见的子目录费用排除。

移除目录且未给新所有者时只停止未来规则识别，保留已经确认的逐笔历史；旧会话自动默认不能继续绕过停用规则认领新消费。转移给另一所有者则整体更新该目录已确定成员。

## 4. 有效目录与权威归属

对 detail 使用已接受的 session cwd；仅缺少本机日志时复用已保存 cwd。当前 cwd 缺失时可复用经哈希／唯一性与否决历史检查的留存历史版本，并在预览中明确展示本次会恢复的目录数。复用既有历史候选规则，不选最近一条来掩盖冲突。

存在真正相反的新观测时不自动采用候选；已接受旧 cwd 仍是旧历史依据，候选待核对。无法确定唯一有效目录的记录不凭项目名称、日期或其他成员数量归入；不把整个 parent／child 会话树当成同一项目。

共享判断次序为：

1. 有唯一已接受目录且命中已明确纳管项目时，目录所有者是该范围的权威；旧逐条例外、持久相反关系和会话默认均不能阻挡。
2. 没有命中任何有效纳管目录时，保留既有明确成员关系以支持停用／换机连续性。没有关系的新成员才使用仍有效的旧模式规则；停止的目录不能通过残留会话默认持续认领新记录。
3. 无法确定则留待识别，不虚构目录。日汇总无会话，继续按完整留存行处理。

每次接受新的明确目录依据时，后续同步／目录刷新会重新判断该会话对应的相关成员，即使已有 NULL 未归属基线，也能纳入已确认目录；因此不需要旧方案的“跳过历史／仅未来”时间水位或按记录自动资格开关。

初次整体采用必须覆盖旧有效人工 override 与相反会话默认：清理／替换受影响会话的旧默认，逐笔记录 directory_binding；以后新增成员从目录判断，不为目录操作建立会跨目录扩展的人工整会话绑定。旧人工接口对已纳管目录的相反写入明确拒绝，防止调用后下一同步才改回的来回跳动。

内容修订／canonical key身份核对仍走原规则，不能借项目统一跳过来源冲突。别名合并中的项目判定也复用目录权威，并保留身份和费用审核。

## 5. 一次预览／一次原子确认

拟增加 Store.preview_project_binding(draft) 与 Store.apply_project_binding(preview_id, idempotency_key)，HTTP为 `POST /api/projects/preview`、`POST /api/projects/apply`；draft 含可选 project_id、name、description、完整 directories。具体类型沿领域规范严格验证，不接受前端指定 affected keys／金额。

预览使用一致读快照计算草稿项目配置、其他项目的精确目录转移、拟纳管模式、全部有依据的成员、元数据恢复和原项目→新项目的变化。新项目预览由后端保留拟创建的稳定 UUID，重复提交不会创建多个同名项目。

结果包括：每目录明细数／会话数与费用，已在目标项目数量、从未归属／其他项目迁入的数量与金额，已占用／待核对口径，目录冲突或无法判定的说明。零成员也可预览并确认保存规则，已归目标项目但仍有旧例外的依据变更同样计入变更摘要。

缓存只保存规范草稿、三修订号、规则／成员／元数据／旧例外摘要和期限，不保存全部事实列表。沿用10分钟有效期、有界元数据和100,000条明细／1,000会话上限；若实际范围超过上限则明确拒绝整个提交，不截取第一页、不要求用户在目录内拆挑记录。本次不增加大规模异步迁移系统。

提交先在事务内检查持久幂等结果，再核对预览期限、三修订号及所有影响摘要；采用 BEGIN IMMEDIATE，冻结候选临时关系，以有界分块更新项目配置／目录所有权／模式设置／必要历史元数据／旧例外和会话默认／逐笔链接／审核事件／受影响投影和日月统计，最后推进修订并保存重放结果。任一步失败全部回滚。明确确认按钮本身是授权动作，审核说明由服务端按实际目录整体绑定生成，不再让用户填写重复的归属理由。

原消费字段、费用版本、record aliases、suppressed／coverage决定、claims和冻结材料均不改变。项目+未归属总量守恒，材料仍按原成员证据冻结；新预览失效，旧ZIP下载原字节。

## 6. 现有接口接续

现有 save_project 可作为内部旧配置门面接续未纳管夹具／旧数据，但对已纳管项目的目录变化必须经过新预览提交；公开HTTP不能绕开影响确认。纯名称／说明且目录完全未变可采用元信息保存路径。

旧 assignments／association assign/reclassify 写入口对命中已纳管目录的相反目标拒绝并提示“请调整目录所属项目”。保留查询和历史审计；高级无目录资料仍走原有限人工处理，不扩散为已纳管目录的逐条例外。

需一起更新原项目合同、数据库合同、页面状态文档和用户README中的旧优先级表述，明确“未确认旧模式”和“已确认目录整体模式”的边界。原先保存目录不静默认领历史的测试保留为未确认旧模式回归，另加确认时整体迁移的测试，不能直接删除历史保护断言。

## 7. 页面状态

项目编辑草稿→正在预览影响→确认目录关联→已保存并刷新，是一条连续流程。按钮可使用“查看关联影响”“确认保存并关联”“返回修改”；不出现未来单独选择、整会话或逐条全选开关。

项目编辑／预览拥有独立 generation、请求序号和稳定提交身份。修改草稿、目标、关闭或同步完成即使旧预览失效；过时成功／409／断连不能清新草稿或重开旧对话框。确认前任何纯预览都不写配置，因此取消不留下只生效一半的项目目录。

提交响应丢失沿原 preview/idempotency_key 重试；已成功但依赖刷新失败提示“已保存关联，刷新结果失败”，只重查结果，不再写入。重启后已提交结果可通过幂等重放或项目列表读取，不能报成未保存并再建一个项目。

常用项目卡显示目录和归属摘要、编辑目录入口；旧逐条选择／会话按钮退出常用主流程。按目录纠错归入管理目录；无目录旧资料处理收纳高级区域。遵循 AhaForms.sync、动态选项、Escape／焦点恢复、窄窗口和既有字号。

## 8. 交付、风险和回退

- 在合成资料与用户库一致副本验证迁移、总量、旧原包和重开；不得以当前聊天的快照数量替代测试，也不直接试写用户原库。
- 实施后交付实际桌面的最终单文件EXE，记录源码依据、SHA、Directory／OneFile独立验收及从桌面副本启动结果。真实台账的一次性应用仍由用户在影响确认界面执行；程序升级本身不等于批准全库转换。
- 不改构建环境／材料代码时按发布合同执行每版自动检查和与改动相关专项，不能把未执行的托盘／Excel／打印写成通过。
- 完整备份保存原项目、归属和材料，必要时恢复到新的资料目录核对；不在线覆盖活动库，不只退回项目配置而留下新统计。新设置与关系使用旧schema可保留数据，但不承诺旧二进制具备新目录整体语义。
- 收尾补实际中文变更片段、清理任务自有临时物并重新核对公开版本和累计待发范围；未获发布授权不公开Release。
