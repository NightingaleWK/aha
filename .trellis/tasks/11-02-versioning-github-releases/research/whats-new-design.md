# 自动 What’s New 的内容与生成方案研究

## 用户决定与当前状态

用户于 2026-11-02 明确选择“自动准备发布 PR、合并后自动发版”，并要求“自动设计每次发版的 What’s New”。本文件记录内容契约的研究依据，最终选择见同任务 `design.md`，尚未实施。

## 推荐呈现

使用简体中文的 Markdown 正文，标题保留 `What’s New · vX.Y.Z`。每个版本按真实内容取用以下结构，空栏目不输出，不靠填充泛泛宣传句撑满：

1. **本次亮点**：一句概括本版最重要的已交付变化；较大功能版可精选少量亮点。
2. **新增功能**：用户新增可完成的事情、适用场景和必要入口。
3. **改进与修复**：体验变化、修复的问题及其可观察影响，按重要性组织。
4. **升级说明**：仅在需要操作、兼容性变化、资料迁移或真实已知限制时出现；破坏性变化置于正文前部突出展示。没有依据时不声称“无需备份”或“所有旧版完全兼容”。
5. **下载与完整变更**：确切版本的 EXE 资源、SHA256 校验说明和对应版本范围的 compare/PR 链接。首次没有前版标签时使用明确源码/提交链接，不构造不存在的比较链接。

下载区和校验值是构建后的机器信息；产品描述必须在发布 PR 阶段即可预览，发布时只填充真实产物链接、校验值与构建记录，不另行改写已审阅的产品陈述。

## 内容来源与自动化边界

推荐采用“开发时由 Codex 写变更说明，Actions 自动组装”的方式：

- 每个用户可感知的改动在功能/修复 PR 内附一份受版本控制的中文发布说明片段。开发代理根据实际源码、PRD和验收结果编写并自检，用户无需在发版时重新作文。
- 片段至少携带稳定标识、分类、标题、用户变化描述及必要的升级注意事项。PR引用由可信提交/PR元数据补充；片段不直接执行代码或模板指令。
- 自动流程按上次已发布版本至候选源码的范围筛选片段，固定排序并按标识去重，组装统一 What’s New，在发布 PR 和版本化说明文件中提供可审阅结果。
- 必须明确处理发布 PR 自身的版本/说明改动、缺失片段、同一PR多片段、撤销变更、纯维护变更和首次引入前的历史变更；缺失重要说明时阻断，不能悄悄依赖一句原始 commit 标题冒充已设计正文。
- 纯内部归档、工作日志和无用户影响的维护可以通过受审阅的理由跳过用户栏目，保留完整变更追溯；不能隐藏有兼容性或安全影响的改动。
- 重要摘要允许在发布 PR 内修改并审阅。自动更新时保留明确的人工覆盖区或要求修改源片段，避免覆盖已审阅内容；以最终合并源码中的说明为发布权威。

这种方式能够在每次发版自动得到内容与排版，并把产品表述纳入同一 PR 审阅，不需要在 CI 中额外调用模型、保存模型密钥或引入付费推理依赖。若未来要求在 GitHub 内独立调用模型润色，则另行明确服务、费用、凭证及生成失败策略；不是当前必需项。

## 官方能力核查

- [GitHub 自动发布说明](https://docs.github.com/en/repositories/releasing-projects-on-github/automatically-generated-release-notes) 默认提供合并 PR、贡献者及完整变更链接，可按标签分类/过滤。它适合变更索引，不能单独保证中文产品叙述、使用场景和升级说明的质量。
- [Release Please 自定义能力](https://github.com/googleapis/release-please/blob/main/docs/customizing.md) 的 changelog 类型支持按 commit 分组或调用 GitHub release-notes API，可配置 changelog sections；需要额外的内容输入与组装步骤来实现这里的产品说明。
- [Release Please manifest 配置](https://github.com/googleapis/release-please/blob/main/docs/manifest-releaser.md) 提供草稿 Release、版本引导及 changelog 配置。应让版本管理和产品说明各有明确权威来源，生成后核对版本、变更范围和对应提交。

## 已收敛的技术选择

最终设计采用 `.release/changes/*.json`、版本化Markdown和发布PR专用预览区。源片段作为人工文案编辑入口，不直接修改生成正文；按最终候选树和最近已公开版本筛选，首次使用bootstrap及明确的首次公开概览。实现必须验证工具的版本识别标记在添加预览后仍有效。

## 原规范与用户确认的新政策

现有 `.trellis/spec/backend/quality-guidelines.md:37` 要求“Windows先目录包真实EXE/浏览器、CSV Excel、HTML A4打印，再构建并验收OneFile”。`delivery-and-cleanup.md:19` 要求实际验收 Directory 后才使用 `--directory-verified`。

GitHub Windows 运行环境能执行原生 EXE 和自动 HTTP/资源/导出检查，但这些结果不证明本机托盘物理交互、Office Excel 或打印实测。用户选择发布PR节奏并不自动等于撤销每版人工门禁。

用户随后明确选择方式1：“首次全面本机验收 + 每版自动检查 + 相关改动追加本机专项”。产品决定已解决，实施时统一更新既有规范，当前规划阶段不提前改生产规范。初次候选资产的回执、以后专项失效规则和草稿恢复见 `design.md`，不把参数标记当成验收结果。
