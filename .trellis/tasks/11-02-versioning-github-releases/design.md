# 版本管理、自动发版与 What’s New 技术设计

## 1. 目标、边界和整体流程

需求以 [prd.md](prd.md) 为准。采用用户确认的发布PR节奏和验收方式1；本文件的技术选择在最终规划批准后实施。

```text
功能/修复PR（代码 + 中文变更片段 + 必要专项验收）
  → 自动质量检查
  → 合入main
  → Release Please准备/更新版本PR
  → 自动补齐What’s New预览，并检查最终PR HEAD
  → 维护者合并发布PR
  → 固定待发布源码SHA，重检版本与验收证据
  → Windows Directory构建及实际验证
  → Windows OneFile构建及实际验证
  → 上传到草稿Release并核对资产
  → 正式公开Release
```

Actions负责仓库自动化，程序保持本机离线运行。发版不访问个人CCS/aha资料，不改变应用schema3、外部CCS兼容集合、核算或历史材料字节。正式发布由维护者合并发布PR决定；机器人不自动合并该PR。

## 2. 单一版本来源及递增

- 权威位置保留 `src/aha/__init__.py` 的字面量 `__version__`，以兼容现有HTTP、页面和新材料消费者。
- `pyproject.toml` 改为动态版本：`project.dynamic = ["version"]`，`tool.setuptools.dynamic.version.attr = "aha.__version__"`。删除第二处人工版本数字；验证实际构建wheel元数据与运行时一致。
- Release Please使用Python策略，明确配置更新 `src/aha/__init__.py`，不能依赖它从发行名 `aha-usage` 猜中导入包名 `aha`。使用受支持的generic extra-file及版本标记；动态pyproject不再写静态版本。
- 版本PR负责唯一一次递增。`.release-please-manifest.json` 是工具状态，不是第二个产品权威来源；CI要求候选工具状态与 `__version__` 一致。
- 保持0.x：`fix`/用户可感知修复升patch；`feat`升minor；0.x破坏性变化升minor并突出升级事项。显式配置pre-major行为，不把功能提交降为patch；1.0升级由审阅明确决定。纯工作日志、归档和无产品影响的文档不单独触发空版本。
- 首个GitHub版本规划为 `v0.4.0`。初始manifest记录本地现有0.3.1基线，bootstrap指向 `f98df67df38a534fb240d20a79dda843297f4437`；保留其后CCS24兼容修复，通过本轮功能提交形成0.4.0候选，不收集全部旧历史自动误升版本。实施前重新核对远端是否出现新提交/标签。
- Windows构建从同一字面量生成PyInstaller `--version-file`：ProductVersion/FileVersion字符串为X.Y.Z，数值为X.Y.Z.0。原生检查Windows文件属性、运行HTTP版本及包元数据一致。
- 发布资产命名 `aha-X.Y.Z-windows-x64.exe`；本机桌面交付仍可名为 `aha.exe`，改名不改变文件内容和SHA256。

## 3. What’s New 内容来源与排版

### 输入

在 `.release/changes/` 保留随功能PR提交的JSON片段，采用Python标准库解析，无需引入运行期依赖。片段字段包括稳定 `id`、`kind`（feature/improvement/fix/breaking/internal）、`title`、中文 `description`、可选 `highlight`、`upgrade_notes`；internal须有审阅可见的排除理由。

片段由开发时的Codex根据实际代码和验收编写。开发约定及PR模板明确要求：用户可感知变更必须提供片段，不能只依赖原始commit标题。CI按变更文件/分类检查缺失，模糊影响范围保守阻断；不能自动证明“中文描述符合实际”，这部分仍在代码和发布PR审阅中负责。

### 版本范围

- 以最近成功公开的Release源码SHA为基线，以候选源码树为终点，从树中选择未发布片段；草稿和失败构建不推进基线。
- 已发布片段不可回写或改用相同id；发布后的纠错用新片段。尚未发布的片段可随功能修订，撤销未发布功能时移除相应片段，最终正文按最终源码树生成。
- 稳定排序并按id去重，冲突/非法字段/缺失必要升级说明直接失败。没有用户内容的内部维护不自动发布空说明。
- 首次没有公开基线时使用明确bootstrap范围，并添加经源码核对的“首次公开发布”能力概览；区分既有能力与本轮新增，不把整个工具的历史功能都称为本版新开发。

### 输出与审阅

输出 `docs/releases/vX.Y.Z.md`，同时在发布PR正文的专用标记区呈现同一正文；保留Release Please的识别标记及技术CHANGELOG。使用统一结构：重要兼容性事项（如有）、本次亮点、新增功能、改进与修复、必要升级说明、下载及完整变更。没有内容的栏目不显示。

生成文件不能直接作为人工编辑入口。维护者修改文案时更新源片段；再次生成保持同一来源，避免机器人覆盖手工改写。发布时只追加确切下载链接、校验值和构建记录，不能另调用模型改写已经审阅的产品陈述。正文、片段集合及版本分别有摘要校验。

默认不在GitHub内调用模型、不要求模型密钥。自动设计由开发时内容编写与发版时可重复组装共同完成；未来独立联网润色另行评估。

## 4. 工作流与权限

建议划分三个入口，复用项目脚本而非复制构建逻辑：

| 文件 | 职责 |
| --- | --- |
| `.github/workflows/ci.yml` | 普通PR检查及显式dispatch的发布PR最终HEAD检查；只读权限，输出明确SHA的检查结果。 |
| `.github/workflows/release.yml` | main事件编排：检查主分支、处理待发布版本、准备/更新版本PR、生成预览、显式触发最终HEAD检查；含受限恢复入口。 |
| `.github/workflows/windows-build.yml` | 可复用Windows质量/构建/产物验证任务，默认只读；Directory通过后才允许OneFile。 |

Release Please action与GitHub官方actions均固定经过核对的提交SHA，并注释对应发行版本；维护依赖时更新固定值及验证记录，不采用浮动第三方main。

凭证首选仓库自动提供的 `GITHUB_TOKEN`。权限按job拆分：源码测试/构建仅contents:read；准备PR需要contents/pull-requests及工具所需issue标签写权限；显式dispatch需要actions:write；发布job需要contents:write。不要把写令牌带入普通PR测试，不用 `pull_request_target` 执行外来源码，不在日志输出启动token或凭证。

当前GitHub允许 `workflow_dispatch` 由默认令牌触发，而机器人创建PR的默认事件可能等待人工批准。因此在更新版本号、What’s New及所有生成文件完成后，取得实际最终HEAD H，再显式dispatch只读CI到该发布分支，携带expected SHA。运行开头核对实际SHA为H；分支继续更新后，旧H的成功不能放行新HEAD。联网验收必须核对仓库必需检查是否接收该HEAD的实际运行结果，不能通过取消保护规则解决漏跑。

主分支发布编排在可信代码中调用API；PR标题、片段、分支名等按数据处理，结构化传参，不拼接为可执行shell文本。只有可信同仓库、目标main、符合预期工具标识及版本文件差异的已合并发布PR才可进入发布；不能凭同名标签冒充发布PR。

## 5. Windows构建与每版自动检查

- 首选固定 `windows-2025`、原生x64 CPython `3.15.2` 和任务venv；2026-11-02已核对Actions官方运行时manifest提供该版本。本项目上一轮本机验收使用3.15.2/SQLite3.53.4，但不能用其历史结果代替当前runner探测。
- 调用现有 `scripts/build_windows.py`，保留固定构建依赖和许可证采集；运行时必须实际通过原有SQLite门禁，不以Python版本号代替探测。
- 每版运行Python完整unittest、Ruff、strict mypy、compileall及现有JavaScript语法/状态测试。修复导致失败的代码或环境，不关闭断言、不降低门禁。
- Directory完成后使用原生EXE及独立合成USERPROFILE/LOCALAPPDATA/data-dir，验证启动、认证HTTP、页面/资源版本和字节、来源23/24合成同步、实际job终态、保存/下载及精确材料、复开同实例、退出后端口/描述符清理；通过后产出可核对的目录验收结果，再传 `--directory-verified`。
- OneFile单独重复必要业务/资源/生命周期检查，核对PE版本；不能把源码服务测试或Directory结果冒充OneFile结果。无桌面CI可用 `--no-browser --no-tray`，该证据明确只覆盖自动检查。
- 生成 `SHA256SUMS.txt`、`build-info.json` 及自动检查摘要，记录版本、待发布SHA、产品指纹、实际运行时/依赖、资产字节数/SHA256和检查范围。只上传确需交付的文件，不上传源码venv、临时资料或runtime.json。

## 6. 首次全面验收与以后专项

实施中将发布政策同步到后端quality/delivery/主契约、前端quality和索引，引用同一份发布合同，避免保留互相矛盾的旧“每版全人工”描述。

采用受版本控制的小型验收回执，记录实际执行的范围、北京时间、产品/相关代码指纹、构建配方及证据摘要；不包含个人路径、真实资料和凭证。首次必须有本机Directory、OneFile、真实浏览器、托盘交互、Excel、A4打印预览/PDF检查。首次GitHub候选资产下载后还需在本机核对SHA、启动和相关业务，不把旧版本记录套用到新产物；确需补齐的人工步骤在首次公开发布前完成。

首次尚无当前候选资产的人工记录时，允许完成检查和候选构建/上传，停在草稿阶段；禁止执行最后的公开动作。首次回执须额外绑定该草稿EXE的实际SHA256及M。人工验收后可通过仅增加回执的受审阅提交更新可信main，再恢复同一M和同一候选资产的发布；回执读取自当次固定的可信main SHA并记录其来源，绝不因此把后来main中的产品代码混入M。若候选资产因重建改变，原资产回执立即失效。此机制只在首次或确需补验时等待，不增加常规无相关变化版本的人工步骤。

以后每次发布自动比较与上次公开版本的相关文件和配方：

| 变化范围 | 要求的本机专项 |
| --- | --- |
| 托盘、启动/退出、实例管理及其调用链 | 托盘交互、复开/退出；按实际影响追加浏览器。 |
| 材料生成、其金额/时间/冻结成员生产链 | Excel导入/数值核对及HTML A4打印预览/PDF。 |
| Python/SQLite/打包依赖、构建入口和配方 | 保守视为影响全部，重新执行全面验收。 |
| 单纯版本数字、生成说明、无相关产品影响的维护 | 每版自动检查；不重复无关人工专项。 |

实现中以明确路径集合及传递影响规则计算指纹，新增生产模块或无法分类的变化不能自动判为“无影响”。版本数字在人工专项指纹中规范化，避免每次升号都触发全人工；其他源码/配方变化不能被规范化掩盖。回执对相应指纹有效，变化后必须重验；CI只证明回执匹配，不声称云端重做过物理交互。证据不足时保持草稿或阻断，不能标记通过。

## 7. 精确提交、发布顺序和失败恢复

以发布PR实际merge SHA M作为标签和构建依据，不直接打包运行时最新main。M必须是可信main的祖先，其版本与候选标签、说明一致；后合入的功能不得混入这一版。

正式公开顺序为：版本/说明校验通过 → M的自动检查和Windows成品通过 → 创建或恢复同M草稿 → 上传EXE/校验/构建信息 → 对照远端资产核对完整性 → 确认全部适用人工回执 → 发布草稿。Release Please若先生成草稿，必须保持draft，直到全部门禁完成；草稿存在不等于已发版。人工记录不充分时PR检查应提前指出，发布仍可生成供验收的候选，但不能推进公开版本基线或把“候选就绪”报告成“发布成功”。

不依赖“默认令牌创建标签再触发另一个workflow”，由同一编排直接调用构建/发布。Release Please的PR创建和Release动作分开调用，明确开启草稿；不假定 `release_created=false` 就不存在需要恢复的草稿，恢复时按版本和M独立查找。

同一版本只允许一个发布状态机，主分支编排使用固定并发组、关闭运行中取消；不能假定GitHub保留所有pending事件。每轮重新扫描已合并但未正式发布的版本，优先恢复最早未完成候选，不因较新main事件到达漏掉版本。未解决候选期间不生成可能混淆版本基线的新发布。

重复执行时：已正式公开且提交/资产匹配则返回已有成功；已公开但不匹配则失败，不覆盖、不移动标签；草稿按归属及M核对后恢复。PyInstaller二进制不承诺跨构建字节完全可重复，若重建得到新SHA，只能在尚未发布的自有候选范围明确重置并重新验收，不能覆盖正式版。下载校验和验收证据必须来自最终选用的同一份产物。

紧急修复以新patch版本发布。设置回退通过受审阅的代码回退或停止工作流完成，保留历史正式版本、标签和校验信息，不删除或回写已经公开的版本冒充回滚。

## 8. 文件影响与工程范围

| 位置 | 计划变化 |
| --- | --- |
| `src/aha/__init__.py`、`pyproject.toml` | 单一版本与动态元数据；保持包名、业务依赖和运行时行为。 |
| `scripts/build_windows.py` | 由权威版本生成PE资源、产物身份及运行时/版本校验，保留原打包入口。 |
| `scripts/release.py` | 发版数据校验、片段/说明生成、候选身份、验收回执及发布恢复；若确有需要按职责拆小，不引入业务旁路。 |
| `scripts/verify_windows_artifact.py` | 可复用原生EXE实际HTTP/材料/生命周期验收入口，隔离合成资料与安全清理。 |
| `.github/workflows/`、Release Please配置 | 质量检查、PR准备、显式CI触发、Windows构建和草稿到正式发布。 |
| `.release/changes/`、`.release/acceptance/` | 可审阅的中文内容片段及小型人工证据回执。 |
| `docs/releases/`、`CHANGELOG.md`、`docs/RELEASING.md`、README、PR模板/开发约定 | 产品说明、维护步骤、未来Codex自动写片段的要求和用户下载入口。 |
| `tests/`及`.trellis/spec/`相关合同 | 意义明确的发版/版本/失败场景回归，更新已获用户批准的验收政策。 |

保持一个集成任务：版本、说明和构建共享同一候选身份，需要共同验收；不为每个文件创建独立任务。

## 9. 上线与外部操作边界

从当前f2e77cb建立 `codex/versioning-github-releases`，保留未合远端的CCS24修复并在设置PR说明包含它；创建分支前再核实工作区及上游状态。

先完成本地实现、独立检查和本机成品验收，再准备可审阅设置PR。仓库可能需要一次性允许Actions创建PR或调整必要权限；实施时读实际设置，无法自动完成时提供明确入口和原因，不提前要求用户提供个人令牌。远端合并及公开发布按具体可审阅结果和已有授权执行。

首次启用后验证真实机器人发布PR、最终HEAD检查和首次Release下载；只有这些都完成，才能把整个发版任务标为完成。应用内更新提醒/安装、代码签名和其他平台不进入本轮。
