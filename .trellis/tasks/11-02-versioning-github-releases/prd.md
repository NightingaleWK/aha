# 版本管理与 GitHub 自动发版

## 目标与用户价值

为持续迭代的 aha 建立可追溯的版本管理与 GitHub 发版机制：版本号、对应源码、面向使用者的 What’s New 及可下载的 Windows 单文件 EXE 保持一致。用户不再需要为每次正式发版手工完成整套打包、编写发布说明和上传操作。

## 当前授权与阶段

- 用户于 2026-11-02 明确同意“创建任务并进入规划”。
- 用户已在最新完整规划审阅后回复“好的”，明确批准实施；当前为 `in_progress`。
- 当前实施并验证本轮功能、准备设置PR；用户随后明确要求合并已有分支、清理已完成工作并同步线上线下。设置PR#1已在最新HEAD CI通过后合并到main，首次发布PR及正式公开继续按下文审阅边界执行。

## 用户已确认的决定

1. 发布节奏 A：功能合入 main 后自动准备/更新发布 PR，维护者合并发布 PR 后自动发版，允许一个版本汇总多次功能合并。
2. 自动设计每次发布的 What’s New；使用中文版产品说明，在发布 PR 中可提前审阅，再随对应版本发布。
3. 发布验收方式 1：首次上线完成本机全面验收；以后每版执行自动检查，涉及托盘、Excel、打印的改动再追加本机专项。实施时据此调整既有发布规范，自动检查与人工验收分别留证。
4. 本地收尾引导：每项工作完成后由代理主动评估是否值得发版、累计待发内容、建议版本、What’s New及验收缺口，完成已授权交付后让用户选择发布、积累或本次无需单独发版；缺条件时先补齐，不自动把开发完成当成发布决定。

## 已确认事实

- 当前本地分支为 `codex/ccs-schema-compatibility`，HEAD 为 `f2e77cb`；创建本任务前工作区干净。
- 本地版本为 `0.3.1`，分别维护于 `pyproject.toml:7`、`src/aha/__init__.py:3`。`server.py:135` 将运行时版本传给页面，材料也使用 `__version__`。
- 2026-11-02 只读查询 GitHub：仓库 `NightingaleWK/aha` 为公开仓库，默认分支为 `main`；远端 `main` 的 `pyproject.toml` 仍为 `0.3.0`，Releases 列表为空，`main` 上 `.github` 路径不存在。不能将本地 0.3.1 当作已经合入 main 或已经发布。
- 已有 `scripts/build_windows.py` 及固定构建依赖。入口要求原生 Windows x64 隔离解释器及 SQLite WAL 修复门禁（`:23-55`）；先构建并实际验证 Directory，再允许 OneFile（`:145-164`），并输出 EXE 路径和 SHA256（`:133-141`）。
- 当前构建命令未设置 Windows PE 文件版本资源；版本管理需涵盖包元数据、程序显示、发布标签及 EXE 身份的一致性。
- `.trellis/spec/backend/quality-guidelines.md:33-43` 和 `delivery-and-cleanup.md:11-29` 规定现有 Windows 验收与桌面交付要求。云端构建成功或无桌面测试不能冒充实际托盘、Excel、打印或桌面副本验收。

## 需求与约束

| 编号 | 需求与约束 |
| --- | --- |
| R1 | 制定明确的版本递增规则，并建立一个权威版本来源；包元数据、运行时、EXE 信息和 Release 标签必须一致，不依赖人工在多处同步数字。当前保持0.x：修复升修订号、新增兼容功能升次版本；0.x不兼容变化升次版本并突出说明，进入1.0及以后的不兼容主版本必须明确审阅，不能自动误升1.0。 |
| R2 | 为提交到主分支的变更建立自动质量检查，检查不通过不得发布正式版本。 |
| R3 | 由 GitHub 的 Windows 执行环境复用既有构建入口，产出可直接使用的 Windows x64 单文件 EXE，遵守运行时及目录包前置验证门禁。 |
| R4 | 每个正式版本在 `https://github.com/NightingaleWK/aha/releases` 提供对应标签、更新说明、EXE 和 SHA256 校验信息，可追溯到确切源码提交及构建记录。 |
| R5 | 发版失败不得展示为成功；重复执行不得静默替换已发布版本的二进制或将旧产物标成新版本。 |
| R6 | 维护者能理解未来一次常规迭代从开发、检查、版本递增到正式发布的操作方式。 |
| R7 | 首次启用前核对本地 0.3.1 与远端 main 0.3.0 的差异及授权，不丢弃已验收的兼容性修复，不凭版本号推断代码已合入。本次规划首个 GitHub Release 为 v0.4.0，包含现有0.3.1修复和本轮发布能力；不补造旧版发布记录。 |
| R8 | 采用用户确认的验收方式1：首次发布完成本机全面验收；以后每版通过自动测试、Windows Directory及OneFile的实际启动/HTTP/资源/导出与生命周期检查，涉及托盘、Excel、打印的变化须有当前相应专项证据。人工证据与相关源码指纹绑定，变化后不能沿用失效记录；无桌面检查不等同于物理交互或Office验收。 |
| R9 | 每次发布自动形成简体中文、面向使用者的 What’s New。说明本次可用变化及必要的升级事项，采用统一易读的 Markdown 编排，能在发布 PR 中提前审阅，并在对应 Release 中发布。内容必须来自本版真实变更，不把计划、未交付功能或未经验证的兼容性承诺写成已完成。 |
| R10 | 发布说明须覆盖用户可感知的功能、改进、修复和必要注意事项；省略没有内容的栏目，排除任务归档、工作日志及纯内部维护噪声。重大兼容性/资料格式变化须突出展示，用户可追溯到相关 PR 或源码。 |
| R11 | 自动说明在同一版本范围内稳定生成、去重；发布 PR 更新后随变更刷新，最终正文与构建源码范围一致。不能在发布 PR 审阅后悄悄替换为未经审阅的新产品描述；若自动生成所需的变更说明缺失，明确阻断或要求补齐，不静默漏项。 |
| R12 | 一次性配置完成后，常规自动检查、构建和发布由GitHub执行，不依赖维护者电脑持续开机；保留维护者合并发布PR这一发布决定。机器人更新发布PR后，检查必须实际对应最终源码，不能用旧的绿色结果或未执行的检查放行。 |
| R13 | 每项工作收尾主动给出发版评估和与实际状态相符的用户选项。区分本次影响与累计待发内容，建议版本及中文说明可审阅；无产品影响的任务无需单独升号，用户选择积累时保留变更，既有明确授权不重复确认，未回复或缺少验收均不能自动公开。 |

## 验收标准

- [ ] AC1 / R1：从权威版本来源可核对程序显示、Python 包版本、EXE 信息和 `vX.Y.Z` 标签；任一不一致阻断发布。
- [ ] AC2 / R2、R3：主分支相关检查及 Windows 原生构建均有可查看的运行记录；使用隔离合成资料实际启动并验证构建产物，Directory 验证通过后才构建 OneFile。
- [ ] AC3 / R4：成功的正式版本在 Releases 可见，下载的 EXE 与发布 SHA256 一致，可找到对应源码提交和更新说明。
- [ ] AC4 / R2、R5：测试、运行时门禁或产物检查失败时不生成可误认为成功的正式版本；重复发版的行为明确且不覆盖已发布内容。
- [ ] AC5 / R6：文档说明修复、功能更新和兼容性变化如何影响版本，并说明维护者在常规发版中的必要动作及失败恢复方式。
- [ ] AC6 / R7：首次发布的源码基线和版本依据有明确记录，区分本地已有版本与远端已发布版本。
- [ ] AC7 / R8：自动验收和人工交互验收分别留证，不把云端无桌面检查等同于桌面 EXE、托盘、Excel 或打印验收。
- [ ] AC8 / R9、R10：发布 PR 可预览完整中文版 What’s New，包含本版真实用户变化、必要升级事项和完整变更链接；正式 Release 保留审阅后的产品说明，有内容才显示相应栏目。
- [ ] AC9 / R10、R11：多项变更、修复版、无用户影响的维护、缺失说明和破坏性变化等场景均有明确结果；同一输入重复生成不重复、不漂移，不混入上版已发布内容或之后才合入的功能。
- [ ] AC10 / R8：首次发布具备对应产品指纹的本机Directory/OneFile、真实浏览器、托盘交互、Excel及A4打印预览/输出验收记录；以后无关改动不要求重复全套人工操作，相关源码或构建环境变化使对应专项记录失效并阻止发布。
- [ ] AC11 / R12：GitHub上真实验证一次功能合并更新发布PR、机器人最终HEAD获得实际自动检查、维护者合并发布PR后完成构建及发布的链路；发布前后不会因默认令牌事件限制而漏跑检查。
- [ ] AC12 / R3、R4、R5：首次正式Release的EXE下载后SHA256、程序版本和运行结果与发布记录一致；源码本地检查、PR检查、候选构建、首次全面验收和正式公开发布分别记录，不互相代替。
- [x] AC13 / R13：AGENTS入口、交付收尾、发布合同及维护说明形成一致的本地发版评估流程；覆盖单独修复、累计功能、纯文档但有待发内容、选择积累及验收不足场景，实际对话给出本轮评估与选择，不改程序或云端触发行为。

## 范围与交付边界

- 本轮规划涵盖版本规则、GitHub Actions 自动检查、Windows EXE 构建、Releases 发布、自动生成与排版 What’s New 和维护说明。
- 暂不扩展到应用内联网检查更新、自动下载安装、Mac/Linux 成品、安装器或付费代码签名。
- 不改核算、来源同步、资料存储、报销流程或冻结材料规则。
- 本机可用成品按现行交付约定在确认实际桌面、文件归属及运行占用后交付，不覆盖来源不明文件或干预用户正在运行的实例。
- 实施后可准备和验证设置PR。远端main合并及首次发布PR合并在相应代码、检查和候选产物可审阅后，按届时已有授权执行；不把本轮规划批准扩大为提前合并尚未实现的代码或绕过维护者的发布决定。

## 风险及延期项

- GitHub仓库首次启用时需核对Actions、机器人创建PR及现有分支规则的实际设置；必要设置的可执行权限在实施阶段核实，不凭本机认证推断连接器或仓库权限。
- Windows执行环境与依赖必须通过现有SQLite门禁；具体运行时探测失败则修复构建环境，不能放宽门禁。
- 外部发布完成依赖设置PR及发布PR实际合入。未执行远端链路时保留AC11/AC12未完成，不能只凭本地测试归档为整个任务已交付。
