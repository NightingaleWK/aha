# 界面与生命周期方案依据

状态：规划建议，最终实施仍需用户在完整方案后确认。

## 用户已经作出的决定

- 用量被有效批次占用后，其他批次不可再次使用。
- 条件内混有可用和占用用量时，只预览及导出剩余可用成员，同时解释排除数量。
- 已报销填错也允许作废释放，原因必填，原记录、金额、状态历史与 ZIP 保留。

## 拟采用的完整生命周期

1. 保存草稿成功即占用，归属稳定的 batch ID；下载成功与否不影响已经保存的占用。
2. 草稿可创建新版本：新版接管有效身份，新旧成员差异在同一事务内调整；失败保留旧有效版及占用。旧版是历史材料，可重下载，不可再修改为第二份有效报销。
3. 已提交先显式撤回为草稿，再修订。撤回须留原因；原包不变，撤回本身不释放。
4. 已报销保持占用和冻结内容。纠错通过显式作废后重新建批次，保留原始报销事实记录；不通过改回草稿直接绕过。
5. 草稿、已提交、已报销都可作废，原因必填；释放全部本批次占用并记录时间、操作者本机事件和先前状态。作废是终态，本版不做恢复/反作废。
6. 普通状态切换、重下载、关闭和重启不释放。每个有效批次只显示一个当前版本的操作入口，历史版本和已作废批次仅供查询、下载。

这些是为独占规则闭合提出的方案，最终评审会明确呈现；不是对用户已报销/已提交状态的外部财务确认。

## 预览与创建

- 新建报销默认“可用用量”。汇总、明细、每日和导出均只使用可用成员。
- 显示所选项目/期间的原始匹配量、排除的已占用或待核对量、剩余可用量，并提供占用批次查看入口。明细数、历史汇总代表请求数和排除行数分别清楚标注。
- 保留“全部用量（查看）”便于核对总消耗；该视图不直接创建新报销，切回可用视图并重新预览后保存。
- 没有可用成员时不能新建报销。它不意味着没有消耗；材料的历史重下载入口保持可用。
- 创建成功后刷新可用范围。另一个窗口抢先占用时，保存返回冲突并要求更新预览，不静默缩减成员或沿用旧金额。
- 人工申请金额继续由用户填写，不根据剩余记录自动按比例改金额；预览范围变化后需让用户明确复核。

## 同批次修订

- 沿用旧版冻结用量时，本批次自身占用不被当作其他批次冲突。
- 若使用当前项目/日期重选成员，修订预览明确以该批次为主体，可纳入自身已有用量和其他未占用用量；其他批次占用仍排除。
- 修订预览应由专门的 batch ID 上下文生成，不能随意给新建请求传一个“排除批次”来绕过独占。保存必须绑定相同批次、有效版本与占用修订号。
- 新版只以草稿创建；历史版不继承有效资格。原 ZIP 与原人工状态历史均不重写。

## 作废提示

文案直述“作废后，此批次不再是有效报销，用量将释放；历史记录与原材料继续保留”。已报销状态同样展示原状态，要求用户自行确认本地记录与实际处理一致，不调用或代替公司财务系统。

## 首期限制

- 本工具只能控制这份本地资料库里的有效占用，不能禁止用户把已下载文件在外部重复提交，也不能跨两个独立复制的资料库联网协调。
- 历史汇总无法按项目/请求拆分；跨粒度疑似重叠只可保守排除并说明，不按比例相减。
- 旧资料若已经有矛盾，保留并标为待核对，不自动选择赢家。允许用户带原因作废不保留的旧申请，再消解占用。

## 受影响链路

`storage.py / migrations` → `claims / batches` → `analysis.py`（唯一汇总）→ `server.py`（批次主体和占用版本校验）→ `web/app.js / index.html / style.css` → `evidence.py`（本次可用筛选依据）→ 隔离数据迁移及 Windows 浏览器成品验证。
